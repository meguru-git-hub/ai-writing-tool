# アプリのセキュリティチェック

このアプリのセキュリティを確認し、重要度つきのレポートを作る。修正はレポートを見たユーザーが選んだものだけ行う。

## このアプリの前提

何を守り、何が現実的な危険なのかを最初に押さえておくと、的外れな指摘や重要度の付けすぎを防げる。

- 個人用で、ふだんは自分のパソコンで `streamlit run app.py` して使う
- 守るべきものは主に2つ
  1. **Gemini の APIキー**：漏れると他人に使われ、無料枠を使い切られたり請求が来たりする
  2. **貼り付けた文章**：受信メールや議事録メモなど、個人情報や社外秘を含みうる
- 現実的な危険
  - キーがファイル・画面・ログ・Git から漏れる
  - Streamlit が同じネットワークの他人から開ける状態で起動され、他人があなたのキーで生成できる
  - 他人が書いた文章（メールなど）に AI への指示が仕込まれる（プロンプトインジェクション）。このアプリの AI は文章を返すだけなので、主な被害は Markdown の画像を使った情報の持ち出し
  - ライブラリの既知の脆弱性
- CLAUDE.md の方針で、データベース・ログイン認証・ユーザー管理は追加しない。対策として「認証を付ける」を安易に勧めず、まず「そもそも他人から開けないようにする」方向で考える。ユーザーが公開したいと言っている場合は、方針とのぶつかり方を説明して判断してもらう

## 手順

### 1. 自動スキャンで手がかりを集める

プロジェクトのルートで実行する（仮想環境がなければ `python` で）。

```powershell
.\.venv\Scripts\python.exe .claude/skills/app-security-check/scripts/scan.py
```

キーの直書き・`.gitignore`・危険なコードのパターン・Streamlit の設定・ライブラリのバージョンを一覧にする。これは文字列の一致で候補を拾っているだけで、誤検知も見逃しもある。「要注意」と出ても実際は問題ないことも、何も出なくても問題があることもあるので、次の手順で必ずコードを読んで確かめる。

### 2. チェックリストに沿ってコードを読む

`references/checklist.md` を読み、A〜D の4つの観点を順に確認する。scan で出た行の前後だけでなく、`app.py`・`gemini_client.py`・`tools.py` と、新しく追加されたファイル全体に目を通す。特に次は scan では判断できないので、コードの流れを追う。

- AI の出力やユーザーの入力が、どの関数で画面に表示されているか
- 貼り付けた文章がプロンプトのどこに、どう囲まれて入るか（`tools.py` の `build_prompt`）
- エラーのときに画面に何が出るか

### 3. ライブラリを確認する

```powershell
.\.venv\Scripts\python.exe -m pip list --outdated
```

既知の脆弱性まで調べるには `pip-audit` が便利だが、requirements.txt 以外のツールを入れることになる。CLAUDE.md のルールに従い、実行する前に理由を説明してユーザーの了承を得る。確認できなかったことはレポートの「確認できなかったこと」に書き、調べていないのに「脆弱性なし」とは書かない。

### 4. レポートを書く

下の形式で、会話の中に出す（ファイルに保存するのはユーザーに頼まれたときだけ）。

### 5. 修正はユーザーが選んでから

レポートを出したら、そこで止めてどれを直すか聞く。セキュリティの修正は動作や使い勝手を変えることがあり（例：同じ Wi-Fi の別の端末から使えなくなる）、それを受け入れるかはユーザーが決めることだから。

ユーザーが選んだら修正し、CLAUDE.md の「動作確認」（AppTest）で全ツールがエラーなく動くことを確かめてから、何を変えたかを報告する。ツールの動きを変えた場合は README.md の表も更新する。

## 秘密情報の扱い

チェックする側がキーを漏らしては意味がない。

- `.env` の中身を Read や `Get-Content` で表示しない。scan.py が値を伏せて確認する
- レポートにキーの値を書かない。見つけた場所を示すときは、先頭4文字と伏せ字（例：`AIza********`）にする
- 本物のキーがコードや Git 履歴に入っていた場合は、ファイルから消すだけでは不十分で、Google AI Studio（https://aistudio.google.com/apikey）でキーを削除して作り直す必要があることを必ず伝える

## 重要度の付け方

| 重要度 | 目安 |
| --- | --- |
| 高 | 今のままで、APIキーや貼り付けた文章が他人に渡る・使われる（例：キーの直書き、`.env` が Git に入っている） |
| 中 | ある条件がそろうと起きる（例：同じ Wi-Fi に他人がいる、悪意のあるメールを貼り付ける） |
| 低 | 起きにくい、または被害が小さいが、直しておくと安心 |
| 情報 | 問題ではないが知っておくとよいこと |

個人用のローカルアプリなので、一般的な Web サービスの基準（CSRF 対策、レート制限、監査ログなど）をそのまま当てはめて重要度を上げない。逆に、実際に起きる筋道があるものは控えめにしすぎない。「誰が・どうやって・何をされるか」を1文で説明できるかを基準にするとよい。

## レポートの形式

ユーザーはプログラミングを学習中なので、専門用語には短い補足を付ける（例：「XSS（画面に仕込まれたスクリプトが動いてしまう問題）」）。

```markdown
# セキュリティチェック結果

## まとめ
（2〜3文。全体の状態と、一番優先して直すべきこと）

| # | 重要度 | 観点 | 問題 | 場所 |
| --- | --- | --- | --- | --- |
| 1 | 中 | 起動・公開の設定 | 同じ Wi-Fi の他人からアプリを開ける | `.streamlit/config.toml`（未作成） |

## 詳細

### 1. 【中】同じ Wi-Fi の他人からアプリを開ける
- **場所**：`app.py:15` など、ファイルと行番号
- **何が起きうるか**：誰が、どうやって、何をされるか
- **直し方**：具体的な変更内容（コード例は短く）
- **用語の補足**：必要なら

## 問題なかった点
（確認して大丈夫だったもの。何を確認したのかが分かるように書く）

## 確認できなかったこと
（ネット接続が必要で調べていない、ツールを入れる了承が必要、など）

## 次のステップ
どれを修正しますか？（例：「1と2を直して」）
```
